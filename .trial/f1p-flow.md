Used gatekit's follow-up change flow: amend `features/F1/brief.md` and `contract.yaml` on the same feature (no `feature new`), update `tasks.md`, implement, write a `spec-review` verdict, run `gatekit drift`, then `gatekit done --feature F1`. The orchestrator quickstart prescribes this because rotation is a change to the same API-key surface, and spec-review is the gate that the spec still tells the truth after the follow-up.
