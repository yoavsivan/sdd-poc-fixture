F1' used gatekit's stock follow-up change flow: amend the existing `features/F1/brief.md` and `contract.yaml` (then `tasks.md`), implement on the same feature id, run `gatekit drift` and `gatekit done --feature F1` until it passes. The orchestrator quickstart says not to create a new feature for a change to the same surface; rotation extends the F1 API-key Settings UI and Bearer contract, so a second feature id would split the spec that `drift` measures against `base`. A `spec-review` verdict is the documented gate that the spec still tells the truth after that follow-up.
